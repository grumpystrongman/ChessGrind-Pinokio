# ChessGrind Chess-Claim Validation and Accuracy Baseline

## Release objective

The knowledge graph and local Ollama coaches can now retrieve verified examples, but retrieval does not make every sentence generated by a language model true. This upgrade adds a deterministic **claim guard** between local model output and the visible/spoken conversation.

The guard is designed to prevent a narrow, high-impact class of false chess assertions without destroying each coach's authored personality. It **does not** certify arbitrary natural-language chess reasoning.

## What is checked

`chess_claim_guard.py` inspects local model responses using the exact python-chess board state and verified prior-move data. It blocks or requests correction for:

- claiming checkmate, stalemate or a finished game when the current legal position does not support that claim;
- naming the wrong king as being in check;
- saying a specific piece occupies a square that is actually empty, occupied by another piece type or wrong color;
- claiming the kings stand adjacent in a legal board or that the starting board is empty (both false statements detected during real MAX testing);
- claiming a forced mate or an exact win without a supplied proof;
- asserting a current winning/losing evaluation without verified current-position analysis;
- attributing next-move certainty to Stockfish when only **previous-move** grading is available;
- giving a concrete "best move is X" or "play X" instruction while a competitive game is underway;
- claiming an illegal move is playable right now when discussing a finished game's board.

If a generated line violates a check, ChessGrind requests one same-personality correction from the installed local Ollama model. If the correction is still untrustworthy, a deterministic board-grounded response is substituted. **The unverified original is not displayed or sent to text-to-speech.**

Response records only outcome codes (accepted, corrected, fallback), coach ID, and event type in `kg_coach_quality`; the quality log never stores chat transcripts or the player's identifying accounts. A local endpoint `GET /api/chess/knowledge/quality` returns aggregate outcomes.

The correction pass preserves the 27 distinct character identity briefs, and the existing conversation memory, speaking voice, and speech-bubble design remain unchanged.

## Coaching reaction bug fixed

The previous prompt applied best/strong/mistake/blunder behavior to a *question* branch instead of the *just played move* branch. That reduced the specificity of live reactions.

Good-move prompts now ask for a concrete consequence or player intention, without reflexive praise. Inaccuracy/mistake/blunder prompts ask for one specific calculation failure or thinking habit, clearly distinguishing Stockfish's previous-position alternative from a suggestion for the current position.

## Engine cache correctness

Engine evaluations were cached by a normalized position key that did not include the fifty-move counter. Because near-draw positions can evaluate differently with different half-move clocks, the cache key now includes `halfmove_clock`. Repetition history still cannot be reconstructed from a bare FEN, so no exact repetition claim can be made solely from cached engine output.

## Independent local engine baseline

`chess_quality_benchmark.py` uses six public, reproducible positions and asks the installed Stockfish for MultiPV at depth 8 and depth 12. It checks that every move in every returned variation is legal and its SAN matches the move on the evolving board.

- 5 of 6 positions kept the same highest-ranked candidate at both depths.
- The **Italian Opening** produced a different top choice at depth 8 versus depth 12.
- The Fool's Mate and Scholar's Mate positions selected the immediate mating continuation at both depths.

The baseline file is `docs/CHESS_QUALITY_BASELINE.json`. This is an instability diagnostic, **not** an accuracy score, perfect-play guarantee, or evidence of optimal engine decisions. A future baseline should include deeper searches, randomized legal positions, puzzles whose solution can be proven, and endgames covered by real Syzygy tablebases.

## Tested

1. Twenty-three adversarial/benign claim fixtures: false mates, fake check, invalid king geometry, empty/wrong piece squares, fabricated engine statements, illegal suggested moves, and valid chess lessons. All passed.
2. Eight deterministic fallback checks across MAX and Vera, including actual checkmate and live check positions. All passed.
3. Mocked model-error test: a false claim was intercepted, rewritten into a permitted response, and logged as `corrected`. When both model attempts were invalid, the final response was a safe deterministic fallback. The knowledge graph, embeddings, and Stockfish retrieval remained usable.
4. Real installed Ollama test against MAX: one opening response and one user question generated, passed selected board claim checks, and produced local aggregate audit records.
5. Six-position engine depth agreement baseline with legal-PV validation.
6. All tests used an isolated copy of the saved ChessGrind SQLite database; existing player histories were not changed.

## Known limitations

The checker cannot prove every tactical or strategic statement in freeform prose. It currently focuses on explicitly recognizable statements; it can miss figurative or indirect errors and sometimes flag ambiguous language. A pass must be described as **selected rule-checkable claims verified**, not as an exhaustive chess-proof certificate. The model can still make subtle conceptual errors, particularly about variations, piece coordination and long-term positional plans.

The optional Syzygy reader is implemented, but actual seven-piece endgame files have **not** been installed. Future work should use those files for exact covered positions and compare multi-depth engine analyses against known labeled chess puzzles before presenting any promise of near-perfect explanations.

## Spoken-response completeness

Model outputs are checked for complete sentences before presentation and speech. If an answer cuts off, ChessGrind retries and can preserve the complete preceding sentences rather than reading an unfinished clause. This is a limited formatting safeguard, not a proof of response quality.
